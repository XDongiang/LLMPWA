> 会话实测记录，2026-10-19。所有数字都来自集群上真实跑过的 sbatch 作业（作业号见文末）。

### 1.6 ⚠️ 旧版的三个真实 bug

对比过程中发现旧版有两处问题（新版均已修正）：

### bug 1：误差棒在海森矩阵的**初始点**求值

```python
args_float = self.args_float          # ← 初始点，之后再没被更新
res = minimize(..., x0=args_float, ...)
...
values = res.x                        # 拟合结果只用来填 fvalue
fvalue = copy.deepcopy(self.args_list)
for i, locate in enumerate(self.float_list):
    fvalue[locate] = values[i]        # ← 只写进 fvalue

args_float_size = (args_float.shape)[0]
my_hessian = onp.zeros([args_float_size, args_float_size])
for x in range(args_float_size):
    v = onp.zeros(args_float_size); v[x] = 1.0
    my_hessian[:,x] = self.thread_hvp(args_float, v)   # ← 用的是初始点！
ferror = onp.sqrt(onp.diag(onp.linalg.inv(my_hessian)))
```

海森矩阵用的是 `args_float`（初始点），而不是 `res.x`（极小点）。新版用 `fitted`：

```python
fitted = onp.asarray(result.x)
hessian = onp.column_stack([hessian_vector(fitted, basis[:, i]) for i in range(n_par)])
```

### bug 2：误差棒大部分是 NaN

旧版写出的 `ferror` 只有 **16 / 92** 个有限值，其余 76 个是 NaN —— 因为初始点处的海森矩阵
不是正定的，`onp.linalg.inv` 之后 `sqrt` 出现负值/NaN。

新版对协方差矩阵取了保护：

```python
ferror = onp.sqrt(onp.maximum(onp.real(onp.diag(covariance)), 0.0))
```

结果 **92 / 92 全部有限**。

### bug 3（次要）：`save_in_json` 把 `save_addr` 当目录

见 §5.2，会在优化成功之后抛 `FileNotFoundError`，导致 npz 也写不出来。

### 1.7 旧版不可复现

旧版每次运行会抽一个随机种子：

```python
num_seed = onp.random.randint(low=0, high=1000000, size=1, dtype='l')
logger.info("random seed: {}".format(num_seed))
onp.random.seed(num_seed)
```

两次完全相同的运行：

| 运行 | 随机种子 | 迭代 | 最终 fcn |
|---|---|---|---|
| 3729325 | `127997` | 61 | `-3092.876499098784` |
| 3729383 | `574020` | 56 | `-3092.851433167758` |

**同一份数据、同一份代码、同样的配置，两次结果差 `0.025`，迭代次数差 5。**
新版没有任何随机性，是确定性的（见 §1.8）。

### 1.8 新版自身的复现性

同一配置跑两次（`3729326` 与 `3729437`，1 卡、全量 23109）：

| 指标 | 结果 |
|---|---|
| 最终 nll | 两次都是 `-3092.874330542225` |
| 迭代次数 | 两次都是 59 |
| `fit_result_values.npy` | **逐位相同**（`np.array_equal` = True） |
| `fit_result_errors.npy` | **逐位相同** |

新版没有任何随机数，**单卡**下完全确定性。对比旧版两次差 `0.025`（§1.7），这是新版的一个实质改进：
结果可复现、可审计。

#### ⚠️ 但是：多卡（4 卡）下新版**也不可复现**

后续补测发现一个此前漏掉的坑：**4 卡运行时，同样的配置、同样的节点，每次给出不同结果**。

同一节点 `g0040` 上三次完全相同的 4 卡作业：

| 作业 | 最终 nll | 迭代 |
|---|---|---|
| 3729583 | `-3089.12091571` | 62 |
| 3729677 | `-3089.14911219` | 60 |
| 3729678 | `-3089.10265367` | 57 |

nll 极差 **0.1417**，是旧版随机种子造成的差异（0.025）的 **5.7 倍**。
换成不同节点再跑，又是新的值（`-3089.00736641` / nit 55，`-3089.14788790` / nit 59）。
轨迹前 9 次迭代逐位相同，**从第 10 次开始分岔**。

**根因（已用实验坐实）**：多卡时对事例轴的 `np.sum` 变成 NCCL all-reduce，
而 **NCCL 默认按拓扑/环境自动挑选算法（Ring / Tree / NVLS）**，不同算法把浮点加法
按不同顺序结合，末位差异经牛顿-CG 放大成宏观分岔。

**决定性实验**：固定 `NCCL_ALGO=Ring` 后，同节点两次运行：

| 作业 | nll | `fit_result_values.npy` |
|---|---|---|
| 3729697 | `-3089.10265367` | — |
| 3729698 | `-3089.10265367` | 与上一次**逐位相同**（`np.array_equal`=True） |

两次 `nll`、`nit`、参数、误差棒**全部逐位一致**。所以这不是代码里的随机数，
而是 **NCCL 归约顺序的不确定性**；固定算法即可完全消除。

**影响有多大**：5 次 4 卡运行之间，参数离散度相对 1σ 误差
最大 `0.514σ`、中位 `0.21σ`，**92 个参数全部远小于 1σ**。
也就是说这 0.14 的 nll 抖动**不改变物理结论**，但它确实存在，
且比旧版靠随机种子造成的抖动更大 —— 想要严格可复现的 4 卡结果，
必须设 `NCCL_ALGO=Ring`（或 `NCCL_ALGO=Tree`）固定归约算法。

**1 卡不受影响**：两次 1 卡运行在不同节点（g0110 / g0104）上仍逐位相同，
因为不涉及跨设备归约。

## 2. 性能对比：7× 到底从哪来

结论先说：**这 7× 基本不是"算得更快"，而是"编译得少"**。
旧版把 **69%** 的时间花在编译上（467 s / 679 s），新版 4 卡只有 34%（32 s / 94 s），
绝对量降了 **14.7×**。运行阶段（牛顿-CG 迭代）单卡对单卡其实是**打平**的，新版甚至略慢。

### 2.1 拆账：三段耗时

![新旧版 × 单卡/4 卡 耗时拆账](phase_breakdown.png)

四个配置**用同一套分段口径**从日志时间戳切出来（四段之和严格等于 `sacct` 的
`Elapsed`，误差 0）：

| 配置 | 编译 | 优化 | Hess+存盘 | 启动/收尾 | **端到端** |
|---|---|---|---|---|---|
| 旧版 1 卡 | 467.2 | 176.8 | 19.4 | 15.6 | **679 s** |
| 旧版 4 卡 | 581.5 | 59.4 | 16.4 | 16.7 | **674 s** |
| 新版 1 卡 | 28.6 | 211.2 | 17.7 | 16.4 | **274 s** |
| 新版 4 卡 | 31.8 | 42.0 | 3.5 | 16.7 | **94 s** |

单位秒。图上每段都标了数值（窄段用引线引到柱外），下表是同一份数据，便于精确引用。

**图上一眼能看出三件事**：

1. **红色（编译）是旧版的全部问题**。旧版 1 卡 69%、旧版 4 卡 **86%** 的时间在编译，
   新版两列分别只有 10% 和 34%。旧版 4 卡的编译比单卡还**更慢**（467 → 582 s），
   因为它让 4 个线程同时编 4 份带完整常量折叠的图，互相抢内存带宽。
2. **蓝色（优化）才是真正"干活"的部分**，而单卡下新旧几乎一样
   （旧 177 s vs 新 211 s，新版反而慢 34 s）。
3. **蓝色只在 4 卡分片时才塌下来**：211 → 42 s（1 卡 → 4 卡，新版内部），
   这是唯一一个来自"并行算得更快"的收益。

**单卡对单卡**（旧 3729383 vs 新 3729326）更能说明问题：端到端 **679 → 274 s**，
省下的 405 s **全部来自编译**（467.2 → 28.6 s，省 438.6 s），
而优化段新版还倒亏 34.4 s。也就是说新版**在单卡上并没有算得更快**，
它只是不用重编那份巨大的常量图。

**从 274 s 再降到 94 s（约 2.9×）**，才来自把 23108 个事例真分片到 4 张卡上。

> 口径说明：端到端用 `sacct` 的 `Elapsed`（旧版 1 卡 679 s），
> 而不是旧版日志里自报的 `Total time: 674.0 s` —— 后者不含 sbatch 启动开销，
> 且新版日志不打印这个量，四个配置无法同口径比较。故全文头条数字统一为
> **679 s → 94 s（7.2×）**；旧版另一次运行 711 s，对应 7.6×。

### 2.2 编译为什么差 16 倍（墙钟 467.2 s → 28.6 s，工作量差 44 倍）

三个互相独立、可分别验证的原因。

#### 原因 A：旧版把数据编成了 XLA 常量，触发 constant folding

旧版 `PWAFunc.__init__` 里把数据 `device_put` 成**实例属性**：

```python
self.data_phif0_kk_3686 = device_put(np.array(cdl.data_phif0_kk_3686), device=self.device)
```

而 `data_likelihood_kk` / `mc_likelihood_kk` 里用 `self.data_phi_kk`、`self.data_f_kk` 读它们。
这些是 Python 闭包捕获的对象，**不是 jit 的 traced 参数**，所以 JAX 把它们当成
**常量烧进 jaxpr**。XLA 拿到常量后会尝试 constant folding —— 对着
**334 MB 的数组**（`mc_int` 单独就 281 MB / 925000 事例）做编译期折叠。

新版把数据作为 **jit 的显式参数**传入：

```python
def nll(args, data): return combined_likelihood(pwaf, args, data)
...
self.jit_nll(self._replicated(x), jax_data)     # data 是运行时输入
```

运行时输入不参与常量折叠。

**日志证据**：

| 日志 | `Constant folding an instruction is taking ...` 出现次数 |
|---|---|
| 旧版 `logs/oldfit2_3729383.log` | **8 次**（单次最长约 4 s） |
| 新版 `logs/kkfit1f_3729326.log` | **0 次** |
| 新版 `logs/kkfit_3728767.log` | **0 次** |

**直接测量**（探针作业 3729480，`run/compile_probe.py`）：同样形状的数组，
闭包常量写法 vs 显式参数写法，测 compile+首次执行：

| 数组规模 | 闭包常量（旧版写法） | 显式参数（新版写法） | 倍数 |
|---|---|---|---|
| 925000 事例 | 1.77 s | 0.06 s | **27.6×** |
| 20000 事例 | 0.09 s | 0.05 s | 1.8× |

小数组几乎无差别，大数组差 27.6× —— 正是常量折叠随数据规模增长的特征。
这直接坐实了原因 A。

#### 原因 B：旧版编 6 份互不相干的图，新版编 3 份且共享子图

旧版 `jit_request()` 一次性造 **6 个独立 jit**：

```python
self.jit_data_likelihood_kk      = jit(self.data_likelihood_kk, device=self.device)
self.jit_mc_likelihood_kk        = jit(self.mc_likelihood_kk, device=self.device)
self.jit_grad_data_likelihood_kk = jit(grad(self.data_likelihood_kk), device=self.device)
self.jit_grad_mc_likelihood_kk   = jit(value_and_grad(self.mc_likelihood_kk), device=self.device)
self.jit_hvp_data_fwdrev_kk      = jit(self.hvp_data_fwdrev_kk, device=self.device)
self.jit_hvp_mc_fwdrev_kk        = jit(self.hvp_mc_fwdrev_kk, device=self.device)
```

6 个图各自都要把同一批数据常量折叠一遍，等于把原因 A 的开销乘了 6。

新版只 jit 一个标量，`grad`/`hvp` 由 autodiff 从这一个标量派生：

```python
def nll(args, data): return combined_likelihood(pwaf, args, data)
grad_nll = grad(nll, argnums=0)
def hvp(args, vector, data):
    return jvp(lambda a: grad_nll(a, data), (args,), (vector,))[1]
return jit(nll), jit(grad_nll), jit(hvp)
```

`hvp` 闭包引用 `grad_nll`，所以 XLA 只编一份梯度图并在 grad 与 jvp-of-grad 之间复用。
**6 份独立折叠 → 1 套共享图 + 0 折叠**。

#### 原因 C：旧版的编译**总工作量**就是 44 倍

`compile_func()` 起 3 个 `Thread`，各自编译一个图（每个线程内部还会按
`thread_gpus` 再起线程）：

| 线程 | 编译耗时 | 起止 |
|---|---|---|
| `thread_likelihood` | 364.2 s | 23:00:45.3 → 23:06:49.5 |
| `thread_grad_likelihood` | 417.2 s | 23:00:45.3 → 23:07:42.6 |
| `thread_hvp` | 467.2 s | 23:00:45.3 → 23:08:32.5 |

三者同时开始，`compile time: 467.19` 就是最慢的那个。这里的并行本身**效率很高**：
总耗时 1248.6 s 压到墙钟 467.2 s，加速 2.67×、效率 89%。所以问题不在并行调度，
而在于**总工作量本身太大**：1248.6 s 的串行编译时间 vs 新版的 28.6 s，
差 **43.7×**。三个线程只是把这个巨额工作量摊到了 3 个核上，
根因仍然是原因 A 的常量折叠 —— 它让每一份图都变贵，编 6 份就是 6 倍。

新版只有一张共享图，28.6 s 编完，没有多余的图需要并行，也就没有 1248 s 要摊。

### 2.3 优化段：单卡其实一样快，提速全部来自 4 卡分片

> 口径：这里的"优化段"是**第 1 次迭代 → 最后一次迭代**的纯迭代跨度，
> 比 §2.1 的 optimize 段少掉"编译完到第一次迭代"的那次求值，
> 这样才能和旧版日志里 scipy 自报的 `time:` 字段同口径比较。

| 配置 | 数据量 | 迭代 | 迭代段墙钟 | 每次迭代 |
|---|---|---|---|---|
| 旧版 1 卡 | 23109 | 56 | 176.8 s | 3.16 s |
| 新版 1 卡 | 23109 | 59 | 195.3 s | 3.31 s |
| 新版 4 卡 | 23108 | 55 | 23.6 s | **0.43 s** |
| 旧版 4 卡 | 23108 | 52 | 59.4 s | 1.14 s |

（旧版 4 卡那行仅供参考 —— 它优化的是被算错的目标函数，见 §2.6。）

**单卡每次迭代 3.16 s vs 3.31 s —— 基本一模一样**（差 4.7%，新版略慢是因为它多迭代了
3 次、且 newton-cg 的 `HesEval` 分布略有不同）。所以旧版在运行阶段**并不慢**，
新版在运行阶段单卡也没有任何算法优势。

迭代段那 **7.5×**（176.8 → 23.6 s）**完全来自把 23108 个事例真分片到 4 张卡上**
（5777/卡，见 §2.5），不是来自梯度/HVP 的实现方式。
注意这只是"优化段"内部的 7.5×，和端到端的 7× 是两个不同的量。

旧版 `Hessian evaluations: 1021`、`Function evaluations: 85`、`Gradient evaluations: 85`
（56 次迭代 → 平均每次迭代 18.2 次 HVP）。新版量级相同。

### 2.4 顺带一提：旧版 HVP 里有一次冗余重算

旧版 `thread_hvp` 在算完两个 jvp 之后，又调了一次 `thread_mc_likelihood(args_float)`：

```python
self.kk_data_hvp[...] = ...jit_hvp_data_fwdrev_kk(args_float, any_vector)[1]
self.kk_mc_hvp_g[...], self.kk_mc_hvp[...] = ...jit_hvp_mc_fwdrev_kk(args_float, any_vector)
self.thread_mc_likelihood(args_float)      # ← 又完整前向跑一遍 mc_lh
```

它只是为了拿 `self.kk_mc_hvp_value = onp.sum(self.kk_mc_hvp_v)`，
而 `jit_hvp_mc_fwdrev_kk` 本来就已经返回了 value。
在 1021 次 HVP 里各多跑一次 925000 事例的前向。这是一个**真实但二阶**的浪费
（否则单卡每次迭代就不会和 3.16 s 打平了）。新版 `hvp` 一次 jvp 拿到全部所需量，没有重算。

### 2.5 单卡 vs 4 卡：分片是数值等价的

要判断"4 卡分片是否引入误差"，必须把**数据量对齐**再比。补测了 1 卡跑 23108
（与 4 卡同数据量，作业 3729649）：

| 配置 | 数据量 | 最终 nll | 迭代 |
|---|---|---|---|
| 1 卡 | 23109 | `-3092.87433054` | 59 |
| 1 卡 | 23108 | `-3089.13552711` | 62 |
| 4 卡 | 23108 | `-3089.00736641` … `-3089.14911219`（5 次，见 §1.8） | 55–62 |

两层结论要分开：

1. **23109 → 23108 少一个事例，nll 变了 3.74**（`-3092.874` → `-3089.136`）。
   这是删掉一个真实事例的物理后果，与并行方式无关。
2. **同样是 23108，1 卡 `-3089.1355`，4 卡落在 `-3089.0074` ~ `-3089.1491`**。
   1 卡的值正落在 4 卡那 5 个值的**散布区间正中**，差异（≤0.14）完全由 §1.8
   说的 NCCL 归约顺序解释，**不是分片引入的系统偏差**。

分片本身（`data_phi_kk global=(23108,) shards=[(5777,)]`）已单独验证为真实 4 路分片。
也就是说：**JAX 的分片对事例轴的 `np.sum` 是数学上透明的**，
唯一的数值效应是浮点加法结合顺序 —— 和旧版那种"每片各算一个全局惩罚项再相加"
的结构性错误（§2.6）完全是两回事。

### 2.6 旧版 4 卡：不仅不快，而且**结果是错的**

前面 §2.3 说旧版只能单卡跑，是因为它的多卡模型在真实数据上**直接崩溃**。
补测把这一点查清了。

#### 崩溃：23109 不能被 4 整除

旧版 `Process_Initializer_Generator.data_npz()` 用
`onp.array_split(arr, num, axis=...)` 切片，`regular()` 里再对切片做
`onp.einsum("ijkl,j->ijkl", onp.array(slices), regular)`。
`23109 = 4×5777 + 1`，`array_split` 给出 `[5778, 5777, 5777, 5777]` 的**参差**列表，
`onp.array(...)` 退化成 object 数组，einsum 立刻炸：

```
ValueError: could not broadcast input array from shape (2,5778,2) into shape (2,)
```

所以旧版在原数据上根本跑不了 4 卡。要测它必须先把数据截到 23108（`data4/`，4 的倍数）。

#### 更严重：即使能跑，4 卡的**目标函数也不是同一个**

在 `data4`（23108 事例）上跑旧版 4 卡，x0 处的诊断探针给出：

| | 1 卡 | 4 卡 |
|---|---|---|
| `data_lh_sum` | `-160990.977188` | `-146385.171702` |
| `mc_lh_sum` | `2044979389.07` | `2044979389.07` |
| `combined` | **`2130.803032`** | **`16736.608518`** |

`mc_lh` 两边完全相同（MC 侧可加 ✓），但 `data_lh` 差了 **14605.8**。

原因在 `data_likelihood_kk` 的结构：

```python
return -np.sum(wt*np.log(np.sum(dplex.dabs(...), axis=1))) + step_function
#      └──────── 对事例可加的主项 ────────┘        └── 全局份额约束，不可加 ──┘
```

`step_function` 是作用在**全部事例汇总份额**上的 lasso 惩罚（阈值 `-1.195` / `-0.188` /
`total_ff=1.589`），它的自变量是**比值** `Σ_k A_k / sum_strong`：

```python
sum_strong = Σ_all_events |A_k|          # 该片内所有事例的汇总
step_function = f(Σ_k A_k / sum_strong)  # 只看比值
```

关键在于**这个比值是尺度无关的**：一片只有 1/4 事例时，分子 `Σ_k A_k` 和分母
`sum_strong` 同时缩到约 1/4，比值几乎不变。所以每片算出的 `step_function`
≈ 全量那一个，而 `thread_likelihood` 做的是

```python
result = onp.sum(self.kk_data_lh) + C*log(onp.sum(self.kk_mc_lh)/925000.0)
#                ↑ 4 片的 (可加主项 + step_function) 全加起来
```

等于把同一个全局惩罚**累加了 4 遍**（多算 3 份）。

反推验证：多算的 3 份 ≈ 14605.8，即单份 ≈ 4868.6，约占 `|data_lh|` 的 3.0%。
`(x-1.195)²×10000` 这类二次惩罚在偏离阈值时到几千是合理的，量级吻合。

**后果**：旧版 4 卡收敛到 `fcn = -2900.85`（52 次迭代），而 1 卡收敛到 `-3089.15`。
差的这 188 就是被重复计入 3 遍的惩罚项。它优化的是一个**不同的目标函数**，
结果不可用。注意这**不是**浮点精度问题，而是目标函数本身被改写，
再多次重跑也收敛不到正确值。

#### 旧版 4 卡性能：更慢

| | 旧版 1 卡 | 旧版 4 卡 |
|---|---|---|
| likelihood 编译 | 361.9 s | 427.7 s |
| gradient 编译 | 416.2 s | 533.8 s |
| hvp 编译 | 459.7 s | 581.5 s |
| **compile time** | **459.7 s** | **581.5 s** |
| `minimize` | 170.0 s | 59.4 s |
| 端到端 | 660.4 s | 667.4 s |

4 卡把 `minimize` 从 170 s 压到 59 s（2.9×），但编译反而**更慢**（459.7 → 581.5 s，
+26%），两边抵消后端到端 **660.4 s vs 667.4 s —— 基本没有变快**。
编译变慢是因为 4 个线程同时编 4 份图（每份都带完整常量折叠），互相争抢内存带宽。

**结论：旧版的多卡路径是坏的** —— 真数据上崩溃，凑成可整除后目标函数又被算错，
而且即使忽略正确性也换不来速度。新版 4 卡（94 s、结果正确、分片数值透明）
是实打实的改进。

### 2.7 显存占用（新旧 × 单卡/4 卡，含时序）

用 `run/vram_sample.sh` 在作业内每 5 s 采一次 `nvidia-smi`，画出全程曲线：

![显存占用随时间变化](vram_timeline.png)

四个子图的 y 轴统一为 0–7400 MiB，可横向直接比较；底色标出编译段与优化段
（边界由日志时间戳换算成"作业开始后秒数"，与采样同一时间原点）。
采样是 5 s 一次，所以曲线画成阶梯状 —— 两次采样之间只知道"保持"，不臆造斜率。

| 场景 | 数据量 | 峰值显存 | 首次采到峰值 | 编译结束于 | 作业 |
|---|---|---|---|---|---|
| 旧版 1 卡 | 23109 | **6722 MiB** | 481 s | 476 s | 3729584 |
| 新版 1 卡 | 23109 | **4636 MiB** | 106 s | 89 s | 3729582 |
| 旧版 4 卡 | 23108 | **3410–3432 MiB / 卡** | 597 s | 595 s | 3729645 |
| 新版 4 卡 | 23108 | **2818 MiB / 卡** | 88 s | 69 s | 3729583 |

"首次采到峰值"总是落在"编译结束"之后的第一个采样点（5 s 粒度），
即四张图的峰值都出现在**编译刚结束、优化刚开始**的瞬间，之后不再增长。
曲线最右端的垂直下落是**进程退出、显存释放**，不是拟合过程中的波动。

**从曲线上能读出四件事**：

1. **旧版单卡全程最吃显存（6.7 GB）**，而且它的曲线是**一路爬升**的：
   编译的 465 s 里从 1.4 GB 逐级抬到 4.2 GB，优化一开始再跳到 6.7 GB。
   这与 §2.2 原因 A 完全吻合 —— 常量折叠把数据一层层实体化进显存。
2. **新版两条曲线都是"到编译末就到顶，之后一条直线"**：1 卡在编译结束（89 s）
   时已到 4.5 GB，106 s 后稳定在 4.6 GB；4 卡在编译结束（69 s）时已到 2.8 GB，
   之后一动不动。说明新版的内存需求在**编译期就确定**，运行期不再增长 ——
   这正是数据作为**显式参数**而非闭包常量的效果。
3. **4 卡的 4 条线几乎完全重合**（新版峰值差 **0 MiB**，旧版差 22 MiB），
   证明事例轴是**真的均分到 4 张卡**，没有哪张卡多扛。
4. **旧版 4 卡的曲线形状和旧版 1 卡一致，只是整体压低** —— 它同样在编译期
   持续爬升，说明常量折叠的浪费在多卡下并没有消失，只是每卡少摊一点。

#### 峰值随卡数下降得比"理想 4 倍"慢，差在哪

单卡 4636 → 4 卡 2818，只降了 1.64×，远不是 4×。把它拆成
**每卡固定开销 `f`**（编译产物、权重、`truth`、XLA 工作区）和
**随卡数均摊的 `s`**（`data` + `mc` 的事例轴）两部分，
用 `f + s = 单卡` 与 `f + s/4 = 4卡` 联立：

| | 固定 `f` | 可分片 `s`（单卡） | 4 卡时 `s/4` |
|---|---|---|---|
| 新版 | **≈2212 MiB** | ≈2424 MiB | ≈606 MiB |
| 旧版 | ≈2335 MiB | ≈4387 MiB | ≈1097 MiB |

（旧版用 1 卡 6722 MiB 与 4 卡最大 3432 MiB 联立；因 4 卡数据是 23108、
1 卡是 23109，这 1 个事例的差异可忽略。若改用 gpu0 的 3414 MiB，
结果只差约 1%，不影响结论。）

这解释了两件事：

- **多卡的收益有上限**。固定项 `f` 约 2.2 GB 不随卡数下降，所以 4 卡最多把
  新版从 4.6 GB 压到约 2.2 GB —— 实测 2.8 GB 已经接近这个地板。
  再加卡（8 卡）收益会很小。
- **旧版要摊的数据量几乎是新版的两倍**（4387 vs 2424 MiB），
  这正是常量折叠展开出来的部分；而固定项两版几乎一样（2335 vs 2212），
  说明固定开销主要是编译产物本身，与代码风格关系不大。

**对申请资源的实际意义**：`gpu` 分区 `DefMemPerGPU=29650`（约 29 GB 主机内存/卡）。
旧版单卡 6.7 GB 显存本身离 16 GB 上限还远，但主机侧（XLA 常量折叠的中间表示 +
数据副本）撑不住单卡的 29.5 GB 配额，这才是 §5 里旧版必须申请 `--gres=gpu:4` 的真实原因。
新版单卡 4.6 GB 显存、主机侧也宽松得多。

## 3. 代码结构差异

| | 旧版 | 新版 |
|---|---|---|
| 并行方式 | `multiprocessing.Process` + `threading.Thread` | `jax.distributed.initialize` + `jax.sharding` |
| 数据访问 | `self.data_xxx`（实例属性） | `data["data_xxx"]`（显式传参） |
| 跨卡通信 | 手工 `Array`/`Lock`/`Barrier` 拼装中间量 | XLA 自动 all-reduce |
| 梯度/HVP | 手写 `thread_grad_likelihood` / `thread_hvp` 公式 | `jax.grad` / `jax.jvp` autodiff |
| 优化器 | 每个进程各跑一遍完整拟合 | 仅 chief 进程跑 SciPy，其余进程 serve 请求 |
| 设备指定 | `jit(..., device=self.device)` | `NamedSharding(mesh, P("event"))` |
| 数据切分 | `onp.array_split(data, num, axis=1)` | `device_put` + sharding spec |
| 复共轭 | `dlib.dplex` | 同左，无 dlib 时用等价 shim |

新版保留了 22 条道的物理表达式、传播子、lasso 份额约束，**逐字未改**，只把数据访问从
`self.X` 改成 `data["X"]`。

### 3.1 旧版手工拆分的梯度公式 vs 新版 autodiff

旧版把组合似然拆成三项手写：

```python
result_kk = sum(data_lh) + 21181.60837312616*log(sum(mc_lh)/925000.0)
grad      = sum(data_grad) + 21181.60837312616*sum(mc_grad)/sum(mc_lh)
hvp       = sum(data_hvp) + 21181.60837312616*(sum(mc_hvp)/sum(mc_lh)
              - <mc_grad, mc_hvp_g, v>/sum(mc_lh)^2)
```

新版直接对同一个标量做 autodiff —— 链式法则给出的正是上面三式，数学上恒等。
第 1 节的数据已经证实了这一点。

## 5. 踩过的坑

### 5.1 ⚠️ 集群上 `rendered_scripts/fit_object_kk.py` 不是用户给的原始版

这是本次排查最大的陷阱。两个文件同名但**是不同的模型版本**：

| 文件 | 大小 | args_list | 自由参数 |
|---|---|---|---|
| 用户提供的原始版 | 125160 B | **219** | **92** |
| `/scratch/caihao1/sunyc/cgpwa_kk/rendered_scripts/fit_object_kk.py` | 83302 B | 123 | 117 |
| 新版 JAX 代码 | — | **219** | **92** |

一开始拿集群上那份跑，得到 `fcn = -3315`，比新版的 `-3089` 还低，看起来像"新版有 bug"。
实际上是**两个不同的拟合**（117 自由参数 vs 92）。换成用户提供的原始版后，
结果立刻吻合到 7 位有效数字。

**教训**：对比前先校验参数个数（`len(args_list)` / `len(float_list)`）与文件 hash，
不要假设同名文件就是同一份。

### 5.2 旧版 `save_in_json` 把 `save_addr` 当目录

```python
with open(save_addr + "/{0}.{1}".format(json_addr, n), 'w') as json_file:
```

`save_addr = "output/fit/fit_result_kk"` 会被当成**目录**。不预建该目录，
旧版会在优化成功、结果全部算完之后抛 `FileNotFoundError`，
连 `save_in_npz()` 都执行不到，npz 也写不出来。跑之前先 `mkdir -p output/fit/fit_result_kk`。

### 5.3 `dlib` 只在旧镜像里有

`from dlib import dplex` 在新镜像里 `ModuleNotFoundError`，新版会退回
`run/base_functions.py` 里逐条对齐的等价实现（`dabs`/`dconstruct`/`ddivide`/`deinsum`）。
旧镜像 `tensorflow.sif` 里有真正的 `dlib`。
